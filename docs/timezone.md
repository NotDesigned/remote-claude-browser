# 出口当地时间与时区

每个浏览器配置必须先绑定出口节点；启动时通过自己的 Mihomo 查询 `https://ipwho.is/`，从同一个 GeoIP 响应读取实际出口 IP、城市、国家和 IANA 时区，并记录检测时间。未分配节点的浏览器配置不能打开。用户设备的所在地不参与探测。

Chrome 进程使用该时区启动，网页、iframe 和 Worker 的 `Date`、`Intl.DateTimeFormat` 保持一致。夏令时由 IANA 数据处理，例如洛杉矶冬季 UTC−8、夏季 UTC−7。工作台顶部时钟显示「城市 · HH:mm」，城市缺失时显示国家，两者都缺失时显示「当地时间 · HH:mm」。地点来自 GeoIP，不从时区名推断；例如出口城市为高雄、时区为 `Asia/Taipei` 时，标签显示高雄。提示和展开信息包含实际地点、完整日期、IANA 时区及 UTC 偏移。时钟使用服务器 UTC 样本校准，设备时钟不准确也不会改变显示的当地时间。

切换出口会关闭该配置的浏览器，同时清除旧检测结果，下一次启动时从新出口重新探测。结果保存在配置记录中，卡片标明「启动时 IP」。运行中的出口缓存探测结果；修改节点内容或重建运行时后重新查询。无法获取有效时区时，启动会明确报错；修复节点连接后可以重新打开配置。

配置卡片 ⋯ 中的「检查出口」探测当前浏览器实际使用的网络。配置尚未运行时只检查绑定节点，并明确标注，不创建浏览器会话，检查完成即释放临时出口。同一个节点可能轮换 IP，因此代理管理中的节点检查不能代替运行中浏览器的检测。检测结果显示连通性、IP、地点、时区和时间；检测时若发现时区与 Chrome 启动时不同，会提示结束该配置的所有会话，等待约两分钟至「运行中」消失后再打开，不会中途重启页面。

CPA 的每份授权按所选节点写入原生 `timezone` 元数据，用于请求中的当地日期。授权完成、绑定变更、恢复和手动检查会同步它；普通 API 请求不逐次查询 GeoIP。未绑定授权停用，保留资料，选择有效节点后恢复；不会回退到部署默认出口或第一个节点。

## 服务进程的时区

`.env` 的 `TZ` 配置网关、日志和系统工具的时区，默认 `Etc/UTC`：

```bash
TZ=Asia/Shanghai
```

Compose 将该值传给入口的 `MIRROR_TIMEZONE`。入口把 zoneinfo 和名称写入 `/data/timezone/`，只读根文件系统中的 `/etc/localtime`、`/etc/timezone` 指向这些文件。无效的 IANA 名称会阻止容器启动。Chrome 按各自出口使用独立的 `TZ`。

`docker compose exec server date -Is` 显示服务进程时间。浏览器时区可在工作台时钟提示中查看，或在对应浏览器中检查：

```js
Intl.DateTimeFormat().resolvedOptions().timeZone
new Date().toString()
```
